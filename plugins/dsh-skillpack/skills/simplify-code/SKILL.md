# Упрощение свежих правок

Четыре узких ревьюера вместо одного широкого: каждый ищет один класс проблем и
не размывает внимание. Идут параллельно — платим задержку одного ревью, а не
четырёх.

**Это не охота за багами.** Правим качество кода, который уже работает: убираем
дубли, снимаем лишнюю сложность, режем расточительство, доводим заплатки до
корня. Поиск ошибок — навык `code-review`.

**Ревьюеры не меняют код.** Их результат — отчёт с доказательствами. Правки
делает основной агент, после свода и только там, с чем согласен.

## Когда вызывать

Триггеры: «упрости», «упрости изменения», «почисти код», «cleanup», «simplify»,
`/simplify-code`. Не запускать сам по себе после каждой правки и не цеплять в
конец несвязанной задачи: это четыре субагента, то есть ощутимые токены.

Модификаторы, которые надо уважать:

- **Фокус**: «упрости с упором на эффективность» — запускается только нужный
  ревьюер (или его находки идут первыми). Фокусы: `reuse`, `quality`,
  `efficiency`, `altitude`.
- **Только отчёт**: «ничего не меняй», «просто покажи» — ревьюеры работают,
  применяется ноль правок, отчёт идёт владельцу.
- **Область**: «последний коммит», «staged», «вот эти файлы» — сужает источник
  диффа (см. фазу 1).

## Фаза 1 — зафиксировать изменения

1. Возьми дифф, начиная с самого вероятного:

   ```bash
   git diff                 # по умолчанию: незакоммиченная рабочая копия
   git diff HEAD            # если пусто — с учётом staged
   git diff --staged        # «staged»
   git diff HEAD~1          # «последний коммит»
   git diff main...HEAD     # «ветка», «мой PR»
   git diff -- путь/файл    # «вот эти файлы»
   ```

   Пусто везде и нечего назвать — скажи прямо, что упрощать нечего, и
   остановись.

2. Запомни **список изменённых файлов** и **намерение**: две-три строки о том,
   что и зачем менялось. Субагенты не видят этот диалог — без намерения они
   примут осознанное решение за случайность.

3. Оцени размер. Больше ~1500 изменённых строк — предупреди владельца, что
   четыре субагента на таком диффе дороги, и предложи сузить (по каталогу, по
   коммиту) до запуска.

4. Сними состояние до работы, оно понадобится как доказательство:

   ```bash
   git status --porcelain
   ```

## Фаза 2 — четыре ревьюера параллельно

Запускай **четыре вызова `subagent` в одном ответе** (в PTC — четыре вызова в
одной программе через `Promise.all`; в стандартном режиме — четыре вызова
инструмента подряд в одном сообщении). `cwd` не задавай: субагент наследует
рабочий каталог сессии. Модель не указывай, если владелец не назвал другую:
субагент наследует настройку профиля, а выдуманный id маршрута сломает запуск.

**Делегирования нет?** Если `subagent` недоступен (режим без субагентов, мы
сами субагент, лимит исчерпан) — не пропускай ревью: пройди те же четыре угла
сам, последовательно, с теми же требованиями к доказательствам, и честно
скажи в итоговом отчёте, что это был один проход, а не параллельный запуск.

### Общий бриф для всех четырёх

Каждому субагенту в промпте:

- Рабочий каталог и команда, которой берётся дифф (например `git diff HEAD~1`).
  Пусть выполнит её сам и **сверит файлы с перечнем** — так он видит свежий
  дифф и полные файлы, а не пересказ.
- **Намерение правки** из фазы 1.
- Файлы целиком по необходимости, поиск по репозиторию (`grep`, `glob`),
  чтение истории (`git blame`, `git log -p`) — это разрешено и ожидается.
- **Только чтение.** `write`, `edit` и любые правки файлов запрещены: любая
  запись в дерево испортит дифф остальным трём.
- Требование к доказательствам: находка без указания `файл:строка` и без
  ссылки на существующий код — мусор, её не пишут. «Где-то есть хелпер» — не
  находка.
- Сначала проверь забор Честертона: перед предложением «это лишнее» сделай
  `git blame` и пойми, зачем строка появилась. Не понял — ставь
  `уверенность: низкая`, а не «удалить».
- Стиль и вкусовщину не писать. Только то, что реально удешевляет поддержку.
- Не больше **шести** находок, отсортированных по цене. Больше — оставь шесть
  самых дорогих и допиши, что осталось за кадром.
- Если `git diff` пуст или не совпадает с перечнем — верни `ДИФФ: empty` и не
  выдумывай находки.

### Формат ответа ревьюера

```text
ДИФФ: ok | empty
ФАЙЛЫ: <сколько файлов и строк насчитал>

НАХОДКИ:
1. файл:строка → проблема → цена (что дублируется / тратится / усложняется) →
   как чинить | уверенность: высокая|средняя|низкая | риск: SAFE|CAREFUL|RISKY
2. ...

ПРИМЕЧАНИЯ: <необязательно: что проверено и чисто, что осталось за кадром>
```

Уровни риска:

- **SAFE** — поведение точно не меняется: мёртвый импорт, комментарий, лишняя
  прослойка, дублирующий `if`.
- **CAREFUL** — смысл сохраняется, но правка заметная: переименование локальной
  переменной, выпрямление вложенных условий, вынос хелпера, слияние дублей.
- **RISKY** — может поменять поведение или контракт: перестройка N+1,
  переименование публичного API, работа с памятью и жизненным циклом,
  изменение обработки ошибок.

### Четыре роли

**1. Переиспользование**

> Найди в диффе код, который повторяет то, что в репозитории уже есть. Ищи по
> утилитам, общим хелперам и соседним файлам (`grep`, `glob`): функции, константы,
> готовые разборщики, проверки окружения, типовые гварды. Помечай: новые функции,
> дублирующие существующие; самодельную логику там, где есть штатная (ручная
> работа со строками и путями, свои проверки env, самописные type guards,
> повторный парсинг). Для каждой находки назови, что именно использовать и где
> оно лежит.

**2. Качество**

> Ищи: лишнее состояние (значения, выводимые из уже имеющихся; кэши, которым
> нечего кэшировать); расползание параметров (флаг прикручен там, где функцию
> надо было перестроить); копипасту с вариациями; протекающие абстракции;
> строки вместо констант и реестров, которые уже есть; вложенные условия на
> три уровня и цепочки тернарников; следы генерации — комментарии, пересказывающие
> код, защитные проверки на уже проверенных данных, `as any` в обход типов,
> приемы, выбивающиеся из стиля файла. Для каждой — конкретная правка.

**3. Эффективность**

> Ищи: лишнюю работу (повторные вычисления, чтение одного файла дважды, дубли
> запросов, N+1); упущенную параллельность (независимые операции идут
> последовательно); утяжеление горячего пути (тяжёлое на старте или на каждом
> запросе); TOCTOU (проверка существования перед операцией вместо самой
> операции с обработкой ошибки); утечки (неограниченный рост, забытая очистка,
> подписки и таймеры без снятия, замыкания, удерживающие весь окружающий
> контекст); чтение целиком там, где хватило бы среза; проглоченные ошибки
> (пустой `catch`, `.catch(() => {})`, `except: pass`, игнор кода возврата).
> Для каждой — правка и чем она дешевле.

**4. Глубина**

> Ищи правки, сделанные не на том уровне: заплатки поверх общей инфраструктуры
> вместо исправления самой инфраструктуры. Признаки: особый случай в общем
> коде ради одного вызывающего (`if (caller == X)`, проверка типа, магическое
> значение); симптом погашен в точке вызова, а у соседних вызовов та же дыра;
> заплатка поверх прошлой заплатки; обёртка, чтобы не трогать то, что правда
> сломано; флаг или конфиг, обходящий сломанный дефолт вместо его починки.
> Назови механизм, который правка обходит, и каким должно быть глубокое
> исправление. Если оно тянет на отдельную задачу — так и скажи: это нормальный
> ответ, а не отговорка. Перед выводом посмотри `git blame` и соседний код:
> совместимость, поэтапные миграции и изоляция вендорного кода выглядят как
> заплатки, но ими не являются — такие не помечай.

## Фаза 3 — свод и применение

1. **Сверь, что код не трогали.** `git status --porcelain` должен совпасть с
   состоянием из фазы 1. Разошёлся — скажи об этом, покажи, что изменилось, и
   не применяй ничего, пока не разберёшься.
2. **Сведи находки** в один список и схлопни пересечения: две находки про одну
   строку или один механизм — одна. Если находку подтвердили двое, она идёт
   выше в очереди: два независимых взгляда — довод.
3. **Выбрось мусор.** Контекста у тебя больше, чем у ревьюера: слабые и неверные
   предложения отбрасывай молча, без спора.
4. **Разреши конфликты.** Ревьюеры расходятся («используй готовый хелпер» против
   «хелпер медленный»). Порядок: корректность → названный владельцем фокус →
   читаемость и переиспользование → микрооптимизация. Взаимоисключающие
   варианты — бери тот, что трогает меньше кода, альтернативу упомяни в отчёте.
5. **Применяй по уровням:**
   - **SAFE** — сразу, пачкой. Затем тесты.
   - **CAREFUL** — по одному файлу, после каждого прогонять тесты этого файла;
     сломалось — откатить именно эту правку и записать.
   - **RISKY** — не применять самому: вынести в отчёт с описанием риска и
     покрытием тестами, решение за владельцем. Находки «глубины» почти всегда
     здесь.
6. **Проверь, что не сломал:** точечные тесты затронутых файлов, затем линтер и
   проверка типов, какие есть в проекте. Гонять весь набор не нужно.
   Правка ограничена диффом и минимальным окружением: переписывать модуль
   целиком — не эта задача.
7. **Отчитайся:** что применено (сгруппировано по роли и уровню риска), что
   отброшено и почему, что осталось владельцу. Если запускал один проход вместо
   четырёх субагентов — скажи это здесь.

## Подводные камни

- **Не расширяй воронку.** Пять-шесть ревьюеров дают не лучшее покрытие, а
  больше конфликтов и расходов. Четыре класса закрывают пространство.
- **Каждому — весь дифф.** Делить дифф между ревьюерами значит терять
  межфайловые дубли и N+1: они видны только целиком.
- **Дифф, а не память.** Ревьюер обязан сам выполнить команду диффа. Пересказ
  изменений в промпте («я добавил кэш в X») — источник вежливых, но пустых
  находок.
- **Правки — не переписывание.** Чистка касается изменённых мест; соседний код
  трогается только на минимально нужное.
- **Не уезжай в баги.** Настоящая ошибка, найденная по дороге, идёт отдельной
  пометкой «нашёл баг» и не смешивается с чисткой.
- **Конвенции проекта сильнее вкуса.** `AGENTS.md`, конфиг линтера, стиль
  соседних файлов — часть брифа ревьюерам, иначе предложения будут воевать с
  домом.
- **Публичные контракты.** Имена экспортов, пути API, имена колонок и ключи
  конфигурации — контракты. Даже неудачное имя переименовывается только как
  RISKY и с решением владельца.
- **Инструменты мёртвого кода врут.** `knip`, `ts-prune`, `depcheck` не видят
  динамических импортов, рефлексии и строковых ссылок. Перед удалением — поиск
  по имени руками.
- **Пустой `catch` бывает осознанным.** Ожидаемая и безвредная ошибка — повод
  пометить, а не удалить.
- **Не всякая заплатка — заплатка.** Совместимость, миграции и изоляция
  вендорного кода. Сомневаешься — `уверенность: низкая`.
- **Субагент мог не ответить.** Один упал — работай с тремя, не перезапускай
  бесконечно; в отчёте укажи, какой угол остался непокрытым.
