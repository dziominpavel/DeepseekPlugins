# Design

## Context

См. `proposal.md` — Why. Ниже только текущее состояние и ограничения, которые
влияют на реализацию.

- DSH `0.2.2-rc.1`, профиль `desktop`. Плагин — npm-пакет с
  `dsh.bundle.patch` и хост-половиной `index.js`; установка только через
  `plugin_manager`, перенос — репозиторий + `install.ps1 -Capture/-Restore`.
- `dsh-skillpack` уже доказал переносимость: пакет читает свои `skills/` и
  `commands/`, регистрирует их через `ctx.skills.register` /
  `ctx.commands.register`, `package.json.files` включает контент, а профиль
  хранит только ссылку `link:`.
- В DSH уже есть нужные точки расширения: `ctx.tools` (`defineTool`),
  `ctx.commands`, `ctx.skills`, `ctx.systemPrompt` (scoped-секции через
  `agent.ctx`), события `agent/created` и `agent/pre-step`, а также обычный
  Node `fs` в хост-плагине.
- Памяти как сервиса нет. `~/.dsh/AGENTS.md` — это инструкции, а не
  агент-курируемые данные; он не даёт лимитов, скана, аудита и автономной
  записи.
- Пользователь хочет запись **без подтверждения**. Поэтому безопасность
  обеспечивается валидацией и аудитом, а не approval-диалогом.

## Goals / Non-Goals

**Goals:**

- Один self-contained пакет `@local/dsh-memory`, который даёт tool, frozen
  инъекцию, навык курации и команду `/memory`.
- Два ограниченных стора (`MEMORY.md`, `USER.md`), автономная запись,
  отклонение небезопасного контента, аудит и undo.
- Перенос кода через репозиторий/`-Restore`, данных — через export/import.
- Не менять поведение существующих плагинов и не требовать правок ядра DSH.

**Non-Goals:**

- `dsh-skill-manager` и самоулучшение скиллов — отдельный change.
- Официальный session-search bundle — включается отдельно.
- Внешние memory-провайдеры, векторный/семантический поиск.
- UI-настройки; в v1 только `/memory`.
- Автоматическое извлечение памяти на каждом ходу: пишет модель через tool.

## Decisions

### D1. Отдельный host-плагин, self-contained

Пакет `plugins/dsh-memory` повторяет форму `dsh-skillpack`:

```text
plugins/dsh-memory/
  package.json          @local/dsh-memory, files: index.js, cordis.patch.yml,
                        skills, locale/*.json, icon.svg, README.md
  cordis.patch.yml      insert: id memory, name '@local/dsh-memory'
  index.js              хост: сторы, tool, инъекция, команда, export/import
  skills/memory/SKILL.md
  locale/{ru,en}.json
  icon.svg
  README.md
```

`cordis.patch.yml` вставляет одну строку `memory`; клиентской половины в v1
нет. Навык лежит в пакете, а не в `dsh-skillpack`: иначе skillpack без
memory-плагина рекламировал бы tool, которого нет.

**Альтернативы:** skill-only в `dsh-skillpack` (не даёт frozen-инъекции и
лимитов); расширение `dsh-skillpack` host-кодом (смешивает переносимый текст и
stateful-поведение); внешний сервис (лишняя инфраструктура).

### D2. Два текстовых стора с жёсткими лимитами

```text
~/.dsh/memory/
  MEMORY.md      заметки агента: факты, конвенции, исправления
  USER.md        профиль пользователя: предпочтения, стиль, окружение
  audit.jsonl
  .history/<target>/<timestamp>.md
  exports/
```

Стор — последовательность коротких Markdown-записей, разделитель — строка `§`.
Лимиты по умолчанию: `MEMORY.md` — 3 000 символов, `USER.md` — 1 500. Считаются
символы содержимого без разделителей; переполнение отклоняется с текущим
использованием, без тихого вытеснения. Файлы остаются человекочитаемыми и
редактируемыми вручную.

**Альтернативы:** один файл (смешивает профиль и заметки); SQLite (не
переносится глазами и не редактируется вручную); векторная БД (избыточно для
нескольких килобайт).

### D3. Автономная запись без approval

Tool применяет `add` / `replace` / `remove` сразу. Никакого `ask`; при
подозрительном содержимом запись **отклоняется** с ошибкой, а не ставится в
очередь. Это соответствует поведению Hermes, которое просил пользователь:
модель решает, когда писать, а не пользователь подтверждает каждую запись.

**Альтернативы:** approval-очередь (ломает автономность); pending-файл с
ручным подтверждением (то же); фоновый extractor (дорого и шумно).

### D4. Frozen system-section на агента

Основной механизм:

1. На `agent/created` плагин читает оба стора один раз.
2. Если есть содержимое, регистрирует секцию через
   `agent.ctx.systemPrompt.section({ name: 'agent-memory', order: 9000, text })`.
3. Текст оборачивается в fence и больше не меняется до конца сессии.

Почему system-section: он не участвует в compaction, остаётся в prefix и
даёт стабильный KV-cache. Запись в текущей сессии меняет файлы и ответы tool'а,
но не секцию; следующая сессия читает новое содержимое.

**Fallback:** если `agent.ctx.systemPrompt.section` недоступен в текущей
композиции, использовать one-shot durable-сообщение через `agent/pre-step`
(как `dsh-time-context`). Тогда память может быть поглощена compaction —
это осознанный компромисс, а не основной путь. Выбор фиксируется в задаче
проверки API.

**Альтернативы:** durable-сообщение сразу (может компактиться и выглядит как
user-роль); динамическая секция на каждый шаг (ломает prefix-кэш); инъекция в
каждое сообщение (шум).

### D5. Tool `memory`

`defineTool` из `@deepseek-ai/dsh-tools`:

```text
action:  add | replace | remove | list
target:  memory | user            (default: memory)
content: string                   (add, replace)
match:   string                   (replace, remove)
```

- `list` возвращает обе секции с использованием и лимитами; работает и без
  активного агента.
- `add` отклоняет точный дубль (no-op с сообщением), переполнение и небезопасный
  контент.
- `replace` / `remove` ищут точное совпадение записи после trim; если точного
  нет — уникальную подстроку. Ноль или несколько совпадений — ошибка без
  изменений.
- Запись требует `exec.agent`, чтобы в аудит попал `sessionId`; без агента
  доступен только `list`.

**Альтернативы:** отдельные tools на каждое действие (раздувает схемы);
whole-file replace (опасно); индексы записей (сдвигаются при конкурентной
записи).

### D6. Security scan

Один сканер используется на записи, импорте и при чтении стора для инъекции.
Категории:

- prompt injection / role hijack (`ignore previous`, `you are now`, `system:`,
  `do not tell`, попытки раскрыть промпт);
- секреты (private key, `sk-`, `ghp_`, `AKIA`, JWT, `password=`, `token=`);
- невидимые и bidi-символы, управляющие символы (кроме `\n`/`\t`);
- попытки закрыть fence (`</memory-context>` и варианты);
- чрезмерные вложенные конструкции, если они маскируют инструкции.

Скан не должен быть параноидальным: паттерны узкие, ошибка называет причину,
пользователь может переформулировать. Отклонённая запись не попадает в стор;
в аудит пишется причина и хеш, **не** сырой секрет.

Внешняя правка файла обходит tool, поэтому скан выполняется и при инъекции:
небезопасный стор не вставляется, сессия продолжается, в лог и `/memory`
попадает предупреждение.

### D7. Аудит, история и undo

- `audit.jsonl` — по строке на попытку: `ts`, `sessionId`, `action`, `target`,
  `outcome`, `reason?`, `charsBefore`, `charsAfter`, `contentHash`,
  `entryPreview?` (для принятых, до 120 символов).
- Перед принятой записью текущий файл копируется в
  `.history/<target>/<ISO-timestamp>.md`; хранится последние N версий
  (`historyLimit`, по умолчанию 20).
- `/memory undo <target>` берёт самую свежую версию, восстанавливает её и
  перемещает использованный файл в `.history/undone/`; повторный undo идёт
  глубже.
- `/memory log [n]` показывает хвост аудита; `/memory list` — использование и
  записи.

### D8. Атомарность и конкурентность

- В процессе — async-mutex на каждый стор.
- Между процессами — lock-файл `~/.dsh/memory/.lock` через `fs.open(..., 'wx')`
  с таймаутом и проверкой устаревшего lock (mtime > 30 с).
- Запись: temp-файл в том же каталоге → `rename`; на Windows при
  `EEXIST/EPERM` — удалить целевой файл под lock и повторить rename.
- Import пишет оба стора как транзакцию: предварительная валидация, бэкапы,
  запись, при ошибке — восстановление обоих.

### D9. Export / import

Формат — один JSON:

```json
{
  "format": "dsh-agent-memory",
  "version": 1,
  "exportedAt": "2026-11-13T00:00:00.000Z",
  "stores": { "memory": "...", "user": "..." }
}
```

- `/memory export [path]`: по умолчанию
  `~/.dsh/memory/exports/memory-<timestamp>.json`; путь можно задать.
- `/memory import <path> [--replace]`: по умолчанию merge (добавить уникальные
  записи); `--replace` заменяет сторы целиком.
- Импорт проверяет формат, версию, размер (≤ 256 КБ), лимиты и скан; при любой
  ошибке не меняет ни один стор.
- Данные не кладутся в пакет и в git: это пользовательские данные.

### D10. Команда `/memory`

`ctx.commands.register` с подкомандами:

```text
/memory                     список и использование
/memory show <target>       полный стор
/memory log [n]             хвост аудита
/memory undo <target>       откат последней принятой записи
/memory export [path]       экспорт
/memory import <path> [--replace]
/memory help
```

Команда не требует approval; destructive-подкоманды (`undo`, `import
--replace`) требуют явного имени. `list`/`show`/`export` работают без
активного агента; запись из команды не выполняется — только управление.

### D11. Навык курации

`skills/memory/SKILL.md`:

- что сохранять: устойчивые факты, предпочтения, исправления, конвенции;
- что не сохранять: секреты, прогресс задач, одноразовые детали, инструкции;
- как: одна запись — один факт, декларативно, коротко; устаревшее — заменять;
- где: `memory` для заметок агента, `user` для профиля; проектные правила — в
  `AGENTS.md`, а не в памяти.

Регистрация через `ctx.skills.register` с `source: 'memory'`, `path` и
`resourceBase`; если `ctx.skills` нет — плагин работает без навыка. Проектный
навык с тем же именем перекрывает пакетный (ранг 250).

### D12. Конфигурация

```ts
interface Config {
  memoryDir?: string          // default: $DSH_HOME/memory или ~/.dsh/memory
  limits?: { memory: number; user: number }  // 3000 / 1500
  historyLimit?: number       // 20
  sectionOrder?: number       // 9000
  scan?: boolean              // true
  audit?: boolean             // true
}
```

`memoryDir` разрешается через `@deepseek-ai/dsh-home-paths`, если пакет
доступен, иначе `DSH_HOME`/`~/.dsh`. Профиль может переопределить `memoryDir`
в своём `cordis.patch.yml`; по умолчанию память общая для всех сессий и
пресетов.

### D13. Упаковка и перенос

- `package.json.files`: `index.js`, `cordis.patch.yml`, `skills`,
  `locale/*.json`, `icon.svg`, `README.md`.
- Установка: `plugin_manager install_bundle target=.../plugins/dsh-memory`.
- После установки — строка в `README.md`, `docs/PLUGINS-GUIDE.md`, `AGENTS.md`;
  снимок профиля `install.ps1 -Capture`.
- Другая машина: клон репозитория + `install.ps1 -Restore`; данные — экспорт на
  старой машине, импорт на новой.
- Между профилями: установить плагин в каждый; `memoryDir` по умолчанию общий,
  при необходимости — свой.
- Между рантаймами: `MEMORY.md`/`USER.md` — обычный Markdown; DSH-плагин —
  один адаптер, не единственный формат.

### D14. Поведение при сбоях

- Нет каталога — создать.
- Файл не читается — предупредить, инъекция пустая, сессия продолжается.
- Секция не зарегистрировалась — fallback на `agent/pre-step`; если и это
  недоступно — предупредить и продолжить без инъекции.
- `ctx.skills` нет — навык не регистрируется, tool и инъекция работают.
- Импорт/запись не удались — стор не меняется, ошибка возвращается модели или
  пользователю.

## Risks / Trade-offs

- **Отравление памяти** → fence, system note «данные, не инструкции», скан,
  аудит, undo.
- **Ложные срабатывания скана** → узкие паттерны, понятная причина, возможность
  переформулировать; аудит отклонений.
- **Секрет в аудите** → для отклонённых записей хранить хеш/длину, не текст.
- **Внешняя правка обходит скан** → скан при инъекции; небезопасный стор не
  вставляется.
- **Prompt cache** → секция заморожена на сессию; записи не переписывают
  промпт.
- **Compaction fallback** → если используется `agent/pre-step`-сообщение, оно
  может быть поглощено; основной путь — system-section.
- **Конкурентные записи** → mutex + lock-файл + temp/rename; тест на две
  сессии.
- **Windows rename** → fallback с удалением под lock.
- **Стоимость схемы tool** → ~300–500 токенов на запрос; лимиты и замер
  `/memory`/token meter.
- **Конфликт имён навыка** → проектный навык перекрывает пакетный; описано в
  README.
- **Общая память между профилями** → это данные пользователя; `memoryDir`
  переопределяется, README предупреждает.
- **Импорт вредоносного файла** → размер, схема, скан, атомарность.
- **Несовпадение API** → `agent/created`/`agent.ctx.systemPrompt.section`
  проверяется первым task'ом; есть fallback.

## Migration Plan

1. Новый пакет; существующие плагины и профиль не меняются.
2. Установить в `desktop`, проверить `plugin_manager` (`fiberPhase: active`),
   создать новую сессию, проверить tool/секцию/навык/команду.
3. Обновить `README.md`, `docs/PLUGINS-GUIDE.md`, `AGENTS.md`; сделать
   `install.ps1 -Capture`.
4. Данные: при первом запуске стора нет; существующие предпочтения из
   `~/.dsh/AGENTS.md` можно перенести вручную в `USER.md` или через import.
5. Откат: `plugin_manager remove_bundle target=@local/dsh-memory`; файлы памяти
   остаются, другие плагины не затронуты.
6. Другая машина: клон + `-Restore`; память — export/import.

## Open Questions

- Подтвердить, что `agent/created` + `agent.ctx.systemPrompt.section` работает
  во всех пресетах (`standard`, `ptc`, `minimal`, `cordis`) и при resume. Если
  нет — fallback `agent/pre-step` уже заложен; поведение спеки не меняется.
- Нужна ли отдельная папка памяти на профиль по умолчанию (сейчас — общая
  `~/.dsh/memory` с возможностью переопределения)? Решается настройкой, не
  кодом.
- Общая папка с Hermes/Claude для кросс-рантаймовой памяти — отдельный change.
